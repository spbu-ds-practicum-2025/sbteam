# План сквозного тестирования URL Shortener (MVP)

## Введение

Данный документ описывает сценарии сквозного (end-to-end) тестирования системы **«URL Shortener»**.
Все тесты предназначены для ручного выполнения и фокусируются на взаимодействии с системой через **REST API** (через API Gateway).

**Охват MVP:**

* Создание сокращённого URL.
* Переадресация по сокращённому URL.
* Обработка истечения TTL.
* Получение метаданных по Short URL.
* Обработка некорректного Long URL.
* Базовая проверка консистентности (master → slave + кэш).

**Предусловия для всех тестов:**

* Система полностью развернута и доступна.
* API Gateway доступен по адресу `http://localhost:8080`.
* Все сервисы (API Gateway, Write API, Read API, Generator, master DB, slave DB, Cache) запущены и здоровы.
* Время на всех узлах синхронизировано (TTL и `expiresAt` зависят от текущего времени).

## 1. Тестирование основной функциональности

### Тест 1.1: Успешное создание короткого URL

**Цель:** проверить корректное создание Short URL по валидному Long URL.

**Предусловия:**

* Доступен любой валидный Long URL, например: `https://example.com/articles/123`.

**Шаги:**

1. Отправить HTTP-запрос:

   ```http
   POST http://localhost:8080/api/shortUrls
   Headers:
     Content-Type: application/json
   Body:
   {
     "longUrl": "https://example.com/articles/123",
     "ttl": 3600
   }
   ```

**Ожидаемый результат:**

* HTTP статус: `201 Created`.
* Тело ответа содержит данные о созданной короткой ссылке, например:

  ```json
  {
    "shortCode": "<string>",
    "shortUrl": "http://localhost:8080/s/<shortCode>",
    "expiresAt": "<timestamp>"
  }
  ```
* Поле `expiresAt` соответствует выбранному TTL (≈ сейчас + 3600 секунд).
* При последующих запросах метаданных (см. тест 3.1) по `shortCode` возвращается тот же `longUrl`.

---

### Тест 1.2: Успешный редирект по действующей ссылке

**Цель:** убедиться, что при переходе по корректному Short URL происходит HTTP-редирект на исходный Long URL.

**Предусловия:**

* Существует активная короткая ссылка:

  * `longUrl`: `https://example.com/articles/123`
  * `shortCode`: `{shortCode}`
    (можно создать в рамках теста 1.1 или в шагах ниже).

**Шаги:**

1. Если ссылки ещё нет — создать её как в тесте 1.1 и сохранить `shortCode`.
2. Отправить HTTP-запрос:

   ```http
   GET http://localhost:8080/api/shortUrls/{shortCode}
   ```

   (либо перейти по `shortUrl` в браузере).

**Ожидаемый результат:**

* HTTP статус: `302 Found`.
* В заголовке `Location` указан исходный `https://example.com/articles/123`.
* При открытии этого ответа в браузере происходит автоматический переход на исходный ресурс.

## 2. TTL и ошибки бизнес-логики

### Тест 2.1: Переход по истёкшей ссылке

**Цель:** проверить, что при истёкшем TTL система не выполняет редирект и возвращает ошибку.

**Предусловия:**

* В системе можно создавать ссылки с малым TTL (например, 1–5 секунд).

**Шаги:**

1. Создать короткую ссылку с малым TTL:

   ```http
   POST http://localhost:8080/api/shortUrls
   Headers:
     Content-Type: application/json
   Body:
   {
     "longUrl": "https://example.com/expired",
     "ttl": 2
   }
   ```
2. Сохранить `shortCode` из ответа.
3. Подождать, пока TTL гарантированно истечёт (например, 5–10 секунд).
4. Отправить запрос на редирект:

   ```http
   GET http://localhost:8080/api/shortUrls/{shortCode}
   ```

**Ожидаемый результат:**

* HTTP статус: `410 Gone`.
* В теле ответа (если есть) указано, что ссылка истекла.
* Заголовок `Location` отсутствует, редирект не выполняется.

---

### Тест 2.2: Переход по несуществующей ссылке

**Цель:** проверить обработку перехода по Short URL, которого нет в базе данных.

**Предусловия:**

* Известен `shortCode`, который гарантированно отсутствует в системе, например: `nonexistent123456`.

**Шаги:**

1. Отправить запрос:

   ```http
   GET http://localhost:8080/api/shortUrls/nonexistent123456
   ```

**Ожидаемый результат:**

* HTTP статус: `404 Not Found`.
* В теле ответа (если есть) указано, что короткая ссылка не найдена.
* Нет заголовка `Location`, редирект не выполняется.

---

### Тест 2.3: Отправка некорректного Long URL

**Цель:** проверить, что система корректно обрабатывает доменно невалидный Long URL и не создаёт короткую ссылку.

**Предусловия:**

* Система запущена, Write API выполняет доменную валидацию URL.

**Шаги:**

1. Отправить запрос с некорректным URL (без схемы):

   ```http
   POST http://localhost:8080/api/shortUrls
   Headers:
     Content-Type: application/json
   Body:
   {
     "longUrl": "not-a-valid-url",
     "ttl": 3600
   }
   ```

**Ожидаемый результат:**

* HTTP статус: `400 Bad Request`.
* Тело ответа содержит информацию об ошибке, например:

  ```json
  {
    "code": "INVALID_LONG_URL",
    "message": "Long URL is not a valid absolute URL"
  }
  ```
* В базе данных **не появляется** новая запись с таким `longUrl`.
* Попытка получить редирект или метаданные по любому `shortCode` из этого ответа (если вообще что-то пришло) не приводит к успешному редиректу.

## 3. Метаданные и консистентность

### Тест 3.1: Получение метаданных по существующей ссылке

**Цель:** проверить корректную работу эндпоинта получения метаданных.

**Предусловия:**

* Существует активная короткая ссылка:

  * `longUrl`: `https://example.com/meta-test`
  * `shortCode`: `{shortCode}`
    (можно создать в шагах теста).

**Шаги:**

1. Создать короткую ссылку:

   ```http
   POST http://localhost:8080/api/shortUrls
   Headers:
     Content-Type: application/json
   Body:
   {
     "longUrl": "https://example.com/meta-test",
     "ttl": 600
   }
   ```
2. Сохранить `shortCode` и `expiresAt` из ответа.
3. Запросить метаданные:

   ```http
   GET http://localhost:8080/api/shortUrls/{shortCode}/meta
   ```

**Ожидаемый результат:**

* HTTP статус: `200 OK`.
* Тело ответа содержит:

  ```json
  {
    "shortCode": "<тот же>",
    "longUrl": "https://example.com/meta-test",
    "createdAt": "<timestamp>",
    "expiresAt": "<timestamp>"
  }
  ```
* `longUrl` совпадает с исходным.
* `expiresAt` совпадает (или очень близок) с значением, полученным при создании.
* `createdAt` не находится в будущем и логически предшествует `expiresAt`.

---

### Тест 3.2: Метаданные по несуществующей ссылке

**Цель:** проверить корректную обработку запроса метаданных для несуществующего `shortCode`.

**Предусловия:**

* Известен `shortCode`, которого нет в системе, например: `meta-not-found-123`.

**Шаги:**

1. Отправить запрос:

   ```http
   GET http://localhost:8080/api/shortUrls/meta-not-found-123/meta
   ```

**Ожидаемый результат:**

* HTTP статус: `404 Not Found`.
* В теле — понятное описание ошибки (ссылка не найдена).
* Никаких побочных эффектов (нет новых записей в БД, кэше и т.п.).

---

### Тест 3.3: Консистентность master → slave (создание + чтение)

**Цель:** убедиться, что запись, созданная через Write API (master DB), становится доступной для чтения через Read API (slave DB).

**Предусловия:**

* Репликация master → slave включена и настроена.

**Шаги:**

1. Создать новую короткую ссылку:

   ```http
   POST http://localhost:8080/api/shortUrls
   Headers:
     Content-Type: application/json
   Body:
   {
     "longUrl": "https://example.com/replication-test",
     "ttl": 600
   }
   ```
2. Сохранить `shortCode`.
3. Подождать короткое время (например, 1–2 секунды), чтобы дать репликации догнать master.
4. Выполнить запрос редиректа:

   ```http
   GET http://localhost:8080/api/shortUrls/{shortCode}
   ```
5. Выполнить запрос метаданных:

   ```http
   GET http://localhost:8080/api/shortUrls/{shortCode}/meta
   ```

**Ожидаемый результат:**

* Редирект:

  * HTTP статус: `302 Found`.
  * `Location: https://example.com/replication-test`.
* Метаданные:

  * HTTP статус: `200 OK`.
  * `longUrl = https://example.com/replication-test`.
* Это означает, что запись из master стала доступна через Read API (через slave DB и/или кэш).

## 4. Кэш и поведение при повторных запросах (опционально)

### Тест 4.1: Повторный редирект по той же ссылке

**Цель:** показать, что повторные запросы по тому же `shortCode` стабильно возвращают один и тот же результат и используют кэш (на уровне демонстрации).

**Предусловия:**

* Существует активная короткая ссылка для `https://example.com/cache-test`.

**Шаги:**

1. Создать ссылку (как в тесте 1.1) и сохранить `shortCode`.
2. Выполнить первый запрос редиректа:

   ```http
   GET http://localhost:8080/api/shortUrls/{shortCode}
   ```
3. Сразу выполнить второй запрос редиректа с тем же `shortCode`.
4. (Опционально, если среда позволяет) временно сделать slave DB недоступной и выполнить третий запрос редиректа.

**Ожидаемый результат:**

* Первый и второй запросы:

  * HTTP статус: `302 Found`.
  * `Location` указывает на одинаковый `longUrl`.
* При отключении slave DB (если к этому моменту кэш прогрелся):

  * третий запрос при корректной реализации кэша всё ещё возвращает `302 Found` с тем же `Location` (чтение из кэша, без доступа к slave).
* Никаких изменений данных в системе эти запросы не вызывают.

## 5. Комплексный сквозной сценарий

### Тест 5.1: Полный жизненный цикл короткой ссылки с TTL

**Цель:** показать полный жизненный цикл Short URL: создание → редирект → метаданные → истечение → ошибка.

**Предусловия:**

* Система развернута.
* Можно задавать короткий TTL (например, 5–10 секунд).

**Шаги:**

1. Создать короткую ссылку:

   ```http
   POST http://localhost:8080/api/shortUrls
   Headers:
     Content-Type: application/json
   Body:
   {
     "longUrl": "https://example.com/full-lifecycle",
     "ttl": 5
   }
   ```
2. Сохранить `shortCode`, `expiresAt`.
3. Сразу выполнить редирект:

   ```http
   GET http://localhost:8080/api/shortUrls/{shortCode}
   ```
4. Сразу запросить метаданные:

   ```http
   GET http://localhost:8080/api/shortUrls/{shortCode}/meta
   ```
5. Подождать, пока TTL гарантированно истечёт (например, 10–15 секунд от момента создания).
6. Повторно выполнить редирект:

   ```http
   GET http://localhost:8080/api/shortUrls/{shortCode}
   ```
7. Повторно запросить метаданные:

   ```http
   GET http://localhost:8080/api/shortUrls/{shortCode}/meta
   ```

**Ожидаемый результат:**

* На шаге 3:

  * HTTP статус: `302 Found`, `Location = https://example.com/full-lifecycle`.
* На шаге 4:

  * HTTP статус: `200 OK`.
  * Метаданные содержат правильные `longUrl`, `createdAt`, `expiresAt`.
* На шаге 6 (после истечения TTL):

  * HTTP статус: `410 Gone`.
  * Редирект не выполняется, заголовка `Location` нет.
* На шаге 7:

  * HTTP статус: `410 Gone`.
  * В истории системы (логах/метриках) видно, что ссылка больше не считается активной.
